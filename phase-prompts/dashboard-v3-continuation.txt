    Expected: active + HTTP 200. Operator refreshes browser → wallet
    panel now shows "▲ 5.78%" (matches top-strip).

A.2 Chart bleed on iOS Safari. Root cause: lightweight-charts uses
    position:absolute for canvas layers. The current
    `relative + overflow-hidden + max-h` doesn't fully clamp on
    Safari because the chart's `autoSize: true` measures the
    container after layout settles AND the canvas can paint outside
    the overflow boundary on Safari.

    Fix approach:
      apps/dashboard-v3/src/panels/ChartPanel.tsx:
        - Wrap chart in a parent with **explicit pixel height** (e.g.
          h-[240px], not min-h/max-h)
        - Inner container: position:absolute; inset:0; overflow:hidden
        - Pass `autoSize: false` AND explicitly call chart.applyOptions
          on a ResizeObserver
      Test on iPad Safari to confirm the canvas stays within bounds.

A.3 Decisions tape spillover. Root cause: the table inside
    `<div className="flex-1 overflow-y-auto">` doesn't get a bounded
    height because the parent grid uses `min-h-[280px]` not a max.

    Fix approach:
      apps/dashboard-v3/src/panels/DecisionsTape.tsx:
        - Replace `flex-1 overflow-y-auto` with explicit max-h
          (e.g. `max-h-[400px] overflow-y-auto`)
        - OR add `h-0 min-h-full` trick to force the table to fit
      apps/dashboard-v3/src/App.tsx:
        - Row C grid cell: add `min-h-0` to allow flex child shrinking

A.4 RTT thresholds too aggressive (UI-only).
      apps/dashboard-v3/src/panels/RTTPanel.tsx (or backend
      provider_rtt.py constants):
        good:   < 300ms  (was 200ms)
        warn:   < 800ms  (was 600ms)
        bad:    >= 800ms

    Plus: fix Chainlink endpoint. `eth.llamarpc.com` returns 403 on
    GET (it's JSON-RPC; expects POST). Either:
      (a) swap URL to a known free public RPC that responds to GET
          (e.g. Cloudflare's eth.cloudflare-eth.com), or
      (b) change rtt_collector.py to use POST for that one URL
          with a noop JSON-RPC body

A.5 Pipeline 0/0 FEEDS fix.
    The bot's `_live.health` aggregator doesn't write feeds_health.json
    on the VPS. Two options:
      (a) Add a tiny VPS-side feeds_health writer service that parses
          bot-staging journal for feed events (~50 LOC). New systemd
          unit `feeds-health-writer.service`.
      (b) Detect feeds via `psutil` — find the bot's process tree,
          look for WS connections, infer health.

    (a) is more robust; (b) is more invasive. Recommend (a).
    DECISION POINT — get operator approval before implementing.

After each fix in A.1-A.5: `make verify` green, `cd apps/dashboard-v3

PHASE B — Polish layer (1-2 hours, optional)
------------------------------------------------------------------------

B.1 Decision-fire markers on chart. lightweight-charts v5 moved
    markers out of the series API into a separate `createSeriesMarkers`
    plugin. Add ▲ (UP) / ▼ (DOWN) markers at each fired-decision
    window_ts on the BTC 5m chart, colored green/red by win/loss.

B.2 Bot-side per-WS-message RTT. The current RTT shows server-to-
    provider HTTP RTT. The bot's actual WS message RTT (from upstream
    timestamp to local recv_ts) is different — typically lower.
    One-line hook in each `src/polymarket_bot/_live/feeds/*.py`:

      self.health.last_rtt_ms = (time.monotonic_ns() - msg.send_ts_ns) / 1e6

    Plus a new field `last_rtt_ms` on the Health dataclass + JSONL
    write in the aggregator. Dashboard renders alongside the
    server-side RTT for comparison.

    DESIGN DOC required: `design/feeds-latency-instrument.md`. Anti-
    vibe rule #1.

B.3 JSON Patch over WS. Currently the WS pump sends full snapshot
    every 1s (~10KB). For multi-operator scale, switch to JSON Patch
    diffs (~80 bytes per tick). Out of scope for v3.0; queue for
    v3.1.

B.4 Code-split the React bundle. Current 561KB (gzip 177KB) is fine
    but warning-level. Dynamic-import the chart + book panels to
    drop initial bundle to ~200KB.

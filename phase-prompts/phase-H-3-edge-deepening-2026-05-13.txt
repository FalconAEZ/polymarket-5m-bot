    H1  REGIME CHANGE: BTC microstructure has shifted since PG's data window
        (2026-05-08 → 2026-05-12). The tier 30-50% × |Δ|<5 cell now fires
        mostly at the high end. Test: bucket bot fires by cell-avg price
        per day. If recent days show drift toward 0.51, regime shift confirmed.

    H2  v2/v2.1 GATE INTERACTION: The bot's `limit_buffer_usd=0.02` ADD 2¢ to
        every ask before computing price_limit and EV. So an ask=0.48 becomes
        price_limit=0.50; an ask=0.45 becomes 0.47. The bot's actual fires
        are price-shifted UP by the buffer. Test: histogram of raw `ask`

        the buffer is the culprit.

        are very small (0.01-0.05), the bot is correctly recognizing thin
        edge but bet_usd is still being computed because bet > min_bet_abs.

SECTION D — MULTI-FIRE REDESIGN (2-6x per window for proven edges)
================================================================================

  CRITICAL CONTEXT — read carefully:

  Last session's H.2.11 throttled multi-fire cap from 2→1 because:
    - Both fires of a multi-fire window ALWAYS settled the same way
    - Both came from the SAME signal at the same instant (within ms)
    - PnL was exactly 2x per-fire PnL — pure capital-variance amplifier
    - WR was IDENTICAL between cap=2 and cap=1 (41.9% on both)

  Operator's ask: "reintroduce per-trade multi-fire not just 2x but 2-6x
  within the 5-min time frame for PROVEN edges"

  HONEST PUSHBACK before designing: simply raising the cap re-creates the
  variance disaster. For 2-6x to be MEANINGFUL, the multiple fires per
  window need to be INDEPENDENT — different signal sources, different
  bet directions, or different price points. Not "fire the same signal 6
  times bigger".

  D.1  ARCHITECTURAL OPTIONS (operator-sign-off required for each):

    Option α — TIME-STAGGERED RE-EVALUATION
      Fire on each significant signal event WITHIN a window. E.g., fire at
      T+30s (initial signal), then re-evaluate at T+90s, T+150s, T+240s as
      price evolves. If signal STILL says fire (different p_win calc
      because spot has moved), fire again. Each fire is a DIFFERENT bet
      because the |Δ| has changed.

      Risk: fires later in the window have less ttl, so price-improvement
            window is smaller. Late fires might be net-negative.
      Test:  back-test the bot history for "fired in same window at T+X
             and T+Y" patterns. Look at the WR diff between early vs
             late fires.

    Option β — MULTI-SIDE FIRES
      Some windows have signals on BOTH sides (e.g., big move up then
      reversal). Currently the bot fires only one direction per signal
      type. A multi-side multi-fire would allow firing UP at T+30s and
      then DOWN at T+150s if the signal flipped.

      Risk: both sides of YES-UP and YES-DOWN can't both win — they're
            mutually exclusive outcomes. Net exposure could be near-zero
            if priced correctly.
      Test:  count windows where Δ flipped sign mid-window (e.g., +10bps
             at T+30 then -10bps at T+180). How many? What's the
             ex-post-optimal trade?

    Option γ — MULTI-CELL FIRES (different EDGE SOURCES)
      Fire ONCE per recognized edge cell. Tier 30-50% × |Δ|<5 = one fire.
      Tier 15-30% × |Δ|<5 = a second fire (if it materializes). Tier
      70-85% DOWN = a third fire. Each is INDEPENDENT — different edges,
      different bet, different decision_id.

      Risk: if the cells correlate within a window (e.g., big BTC move
            pushes multiple tier prices to qualifying ranges), still
            correlated bets.
      Test:  audit current bot history — how many windows had MULTIPLE
             distinct cells signal-ready simultaneously? n probably small.

    Option δ — DCA / LADDERED ENTRY
      Single signal, but split the Kelly bet across 2-6 fires at
      different price points as the orderbook evolves. E.g., bet 1/3
      at the first signal, second 1/3 if price improves, third 1/3 at
      ttl end. Same direction, different fill prices.

      Risk: complex. Adds maker-fill simulation complexity.
      Test:  audit windows where the ask moved significantly during the
             ttl. How often does the orderbook offer DCA opportunities?

  D.2  MY (Claude's) RECOMMENDED PRIORITIZATION

    1. Option γ (multi-cell) is the CLEANEST. Each cell is a PG-grounded
       edge with its own data. Different cells have different correlations
       — if 30-50% and 70-85% DOWN both fire in the same window, they're
       betting on the same outcome (the bot bets WITH the larger move)
       so they ARE correlated. Not as clean as I hoped on second thought.

    2. Option α (time-staggered) is the most DATA-WORTH. Back-test it
       against the bot's 4000+ historical decisions — find windows where
       a later fire would have HAD a different bet from an earlier fire
       (because Δ changed). If that subset shows DIFFERENT WR/PnL than
       the early-only set, option α has real edge.

    3. Option β (multi-side) requires the SAME WINDOW to have signals
       in OPPOSING directions over the 5min. Historically rare but
       intriguing. Test the data before coding.

    4. Option δ (DCA) is sophisticated but requires re-architecting the
       simulator + the fill model. Defer to a later phase.

  D.3  WHAT THIS SESSION SHOULD PRODUCE FOR MULTI-FIRE

    NOT code. The session produces:
      (a) Data-backed analysis of each option α/β/γ/δ — what's the
          historical edge if we'd been firing each pattern?
      (b) Operator-recommendation: which to ship, which to defer.
      (c) Spec for the chosen option — ready for a future H.3.X code
          session.

    If H.3 ships any code for multi-fire, it must be:
      - Backward-compat with the current cap parameter
      - Operator-flagged off-by-default
      - Heavily tested (40+ tests) — multi-fire is the highest-risk
        invariant in the bot

WHY THIS PRIORITY ORDER (the meta-reasoning)
================================================================================

  Regime-detection (whether Akash's HMM/LSTM or simpler vol-ratio) is a
  2nd-order MODULATOR — it tells the bot "should I fire in current
  conditions" but doesn't generate new signal.

  ADAPTIVE PRIORS is a 1st-order EDGE GENERATOR — it makes the bot's
  static-data assumptions become continuously-updated empirical truth.
  Self-corrects across regime drift without needing to classify regimes.

  Order of operations matters: fix known signal degradation BEFORE adding
  filters. A regime filter on a leaky signal still produces leaky output.

  Concrete: our CH3 cell is firing at WR=48.1% (exactly Phase G historic)
  but $/trade=-$0.39 because cell-avg-price is 0.51 not 0.40. A regime
  detector could explain the drift; an adaptive priors layer would FIX it
  by re-weighting recent fires. Different tools, different roles. Fix
  first, modulate later.

SECTION E — ADAPTIVE PRIORS DESIGN (real edge work — DESIGN ONLY THIS SESSION)
================================================================================

  This is the centerpiece of H.3 forward. DESIGN it; don't code it this
  session. Operator sign-off required before coding lands.

  E.1  THE CORE IDEA

       Phase G's spot_aware_priors.json is STATIC — built from 5 days of
       2026-05-08→12 historical data. The cell-avg-price drift discovery
       proves market microstructure has shifted since then. Static priors
       can't track this shift.

       Adaptive priors = the priors_table values UPDATE based on the
       bot's OWN trade outcomes. Rolling window. Bayesian-style update
       with a prior weight (don't let one bad day flip everything).

       Math:
         For each (tier, delta-bucket, side) combo:
           p_win_adaptive = (w_static × p_win_static + w_rolling × p_win_observed)
                          / (w_static + w_rolling)
         where:
           w_static  = some fixed weight (e.g. 100) — anchor to Phase G
           w_rolling = count of recent fires in this combo (capped, e.g. 200)
           p_win_observed = observed WR in rolling window

       Initially when w_rolling=0, p_win_adaptive = p_win_static (Phase G).
       As fires accumulate, p_win_adaptive shifts toward observed.

  E.2  WHY THIS BEATS REGIME DETECTION

       A regime detector says "we're in regime X; apply rule Y." Static
       rule against changing markets eventually fails.

       Adaptive priors say "this exact cell has shown p_win=X over the
       last 100 fires; use that." Self-correcting. No regime
       classification needed.

       Equivalent: regime detection compresses market state into a
       handful of labels; adaptive priors learn the cell-level state
       directly. Higher resolution, no labeling needed.

  E.3  PROPOSED ARCHITECTURE

       Component A — RollingCellStats
         Tracks per (tier_label, delta_bucket, side) combination:
           - last_N_outcomes: deque[bool]  # max 200
           - last_N_pnl: deque[float]      # for $/trade tracking
           - p_win_observed property = sum(last_N_outcomes) / len()
         Persisted to disk every K updates (default K=10) so survives
         restart.

       Component B — AdaptivePriors (wraps SpotAwarePriors)
         lookup(price, abs_delta_bps) → float | None
         Algorithm:
           1. real_p_win = real_priors.lookup(price, abs_delta_bps)
              (or fallback to 0.48 if miss + tier_relax)
           2. cell_stats = stats_for(tier, delta_bucket, side)
           3. if cell_stats.n >= 30:
                blended = (W_STATIC * real_p_win + cell_stats.n * cell_stats.p_win_observed)
                        / (W_STATIC + cell_stats.n)
                return blended
           4. else: return real_p_win

       Component C — runner integration
         After each settle, call adaptive_priors.observe(cell_key,
         won, pnl_usd). Periodic disk persistence.

  E.4  TUNABLES
       - PRIORS_ADAPTIVE_ENABLED (default false; opt-in for safety)
       - PRIORS_ADAPTIVE_STATIC_WEIGHT (default 100; controls inertia)
       - PRIORS_ADAPTIVE_ROLLING_WINDOW (default 200; size of recent)
       - PRIORS_ADAPTIVE_MIN_N (default 30; min sample to use blended)

  E.5  RISKS
       - Overfit to recent: a bad streak could push priors below real.
         The static-weight anchor mitigates but doesn't eliminate.
       - State persistence: rolling deques must survive bot restart.
         Use same JSONL replay pattern as BankrollTracker.
       - Backward compat: must work alongside CH3 fallback (priors miss
         + tier_relax + |Δ|<5 → fallback 0.48). Adaptive priors should
         layer ON TOP of, not REPLACE, the fallback.
       - Operator-readable state: dump current adaptive p_win table to a
         JSON the dashboard can show.

  E.6  WHAT THIS SESSION DELIVERS
       A spec doc (design/adaptive_priors.md) covering all of E.1-E.5.
       Operator sign-off. NO code this session. Code lands in H.4.

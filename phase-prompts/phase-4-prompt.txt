  - Why paper mode exists (validate the FillSimulator against live
    microstructure before risking real money). Reference checkpoint_phase_3
    diagnostic: backtest produced -$6.16 P&L on 60% win-rate over 15 fills,
    so the paper run must show whether that's (a) the simulator
    being optimistic, (b) the fee model being wrong, or (c) the strategy
    actually being unprofitable at this size.
  - Architecture: ShadowBook receives Decisions from Strategy, simulates
    fills against the *live* orderbook seen at decision time (NOT the next
    book like backtest does — paper sees the same book the live bot would).
    Imports stay one-way: `_paper` may import `_live.feeds` (read-only) but
    never `_live.execution`; production never imports `_paper`. Enforced
    by the existing import-linter contracts.
  - Decision-logging schema: every decision writes a JSON line with the
    full input snapshot (orderbook, oracle state, deterministic composite,
    rationale, simulated fill, simulated P&L). Stored at
    `state/decisions/<UTC-date>.jsonl`. Goal: postmortems and Phase 8
    ensemble re-runs can replay against this.
  - Sim validation methodology: how task 4.3 will pick 100 hypothetical
    decisions, how it pulls the actual top-of-book at each timestamp, how
    it computes the ≥90% within-1¢ criterion.
  - What is OUT of scope this session: the 14-day run itself, daily
    PnL ritual, regime-coverage analysis. Those are future-session work
    triggered when the gate is ready to fire.

Lock the doc, commit it, then write the code.

TASK 4.1 — Paper-mode runtime
------------------------------------------------------------------------

Files:
  - `src/polymarket_bot/_paper/__init__.py`
  - `src/polymarket_bot/_paper/shadow_book.py`
      ShadowBook: maintains the latest BookUpdate per (asset_id, side).
      `attempt_fill(decision: Decision, now_ts_ns: int) -> Fill | None`
      simulates against the most recent book seen for the decision's
      asset_id. Reuses `FillSimulator` math from
      `src/polymarket_bot/backtest/fills.py` so the cost model is identical
      between backtest and paper.
  - `src/polymarket_bot/_paper/runner.py`
      PaperRunner: subscribes to live MarketEvents (via the existing
      `_live.feeds` interfaces), drives a Strategy, queues decisions,
      attempts fills as new BookUpdates arrive within `decision.ttl_s`,
      writes settlement P&L to the decision log on window close.

Tests:
  - `tests/paper/test_shadow_book.py` — unit tests with synthetic
    BookUpdates: fill / no-fill / TTL expiry / size-cap behaviour
    matches the backtest FillSimulator on identical inputs.
  - `tests/paper/test_runner.py` — drive PaperRunner with a fake feed
    that yields a fixed event stream, assert the resulting decision log
    is shape-correct.

Import-linter:
  - Add a contract: `_paper` may import `_live.feeds.*` but never
    `_live.execution.*`. Existing two contracts stay.

TASK 4.3 — Sim validation harness  (data-permitting partial)
------------------------------------------------------------------------

`scripts/validate_paper_sim.py` — given a captured date range, picks N
hypothetical decisions (deterministic strategy at threshold 0.6pp,
randomly across the windows), then for each:
  1. Records the simulated fill price the FillSimulator would produce.
  2. Looks up the actual top-of-book at the decision's intended fill
     timestamp (decision.ts_utc_ns + small latency budget).
  3. Computes the absolute delta in cents.

Outputs a report: count of decisions, mean / median / p95 delta, and
the within-1¢ pass rate. Target per RUNBOOK §4.3: ≥ 90% within 1¢.

Run it against the existing captured data (2026-05-06 + 2026-05-07).
Capture output to `runbooks/gate-evidence/phase-4.3-sim-validation.txt`.
If the pass rate is < 90% on the hours-of-data sample, that's
diagnostic — write up the gap in the decision log and let the 14-day run
provide the real validation.

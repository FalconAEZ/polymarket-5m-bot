Yesterday's audit (2026-05-10):

  total settled: 22
  resolved via polymarket (instant): 0   ← gamma poll FAILS 100% of the time
  resolved via polymarket-recovery:  1
  resolved via chainlink-fallback:   21
  matched gamma truth:               14 (67%)
  MISMATCHED gamma truth:             7 (33%)
  bankroll over-stated by:           +$6.34

Two distinct problems:

A) **Gamma instant-settle never succeeds in production.** Bot polls
   gamma every 1s for 30s after window close. ALL 21 chainlink-
   fallback settles came after the 30s timeout fired. Yet manual
   curl of gamma a few minutes later returns the truth (closed=true,
   outcomePrices=[1,0]). So gamma DOES resolve — just not within
   our 30s polling window, OR our polling-loop is hitting a stale
   CDN response.

   Hypothesis: gamma returns `closed=false` with cache TTL ~30s. We
   poll for 30s, all queries hit the cached "not closed yet"
   response. By the time the cache expires, our timeout has fired.

B) **Chainlink-local-fallback is wrong ~33% of the time.** The
   bot's `_state.close_oracle` is the latest OracleUpdate it saw
   via WebSocket before window close. Polymarket's on-chain
   settlement uses a different/later chainlink reading. Even tiny
   timing differences flip the answer when the spot move is small
   (most windows are < ±5bps total = sub-tick chainlink).

   Concrete example from yesterday: window 1778387400.
     fired UP at fill 0.911
     bot's open_oracle=80819.29, close_oracle=80812.415
     chainlink says: close < open → DOWN → bot recorded -$5.00
     gamma says: outcomePrices=["1","0"] → UP won
     actual pnl was +$0.49

------------------------------------------------------------------------

With the background-settle architecture (commit 43872e9, validated),
a long gamma poll doesn't block anything. The 30s timeout was sized
for a synchronous-call era; we can extend it generously now.

  src/polymarket_bot/_paper/runner.py:

                                              ↓
    DEFAULT_INSTANT_SETTLE_TIMEOUT_S: float = 300.0  # 5 min

  Or via env:
    INSTANT_SETTLE_GAMMA_TIMEOUT_S=300  in .envrc

Plus consider increasing interval from 1s to e.g. 5s — with 5 min
window we make ~60 polls. Reduces gamma load + sidesteps the
1s-cache-TTL hypothesis.

ITEM 3 — Post-hoc gamma re-resolution (~1-2h)
------------------------------------------------------------------------

Even with longer timeout, gamma might still occasionally fail (UMA
slow, network blip). Need a SECOND chance: after a chainlink
fallback fires, schedule another gamma retry 5-10 minutes later.

Sketch (in `_do_settle` after chainlink fallback writes settled):

  if resolution_source == "chainlink-local-fallback":
      task = asyncio.create_task(
          self._post_hoc_gamma_retry(snap, settled_ts_ns),
          name=f"post-hoc-gamma-{snap.window_ts}",
      )
      self._pending_post_hoc_retries.add(task)
      task.add_done_callback(self._pending_post_hoc_retries.discard)

  async def _post_hoc_gamma_retry(self, snap, original_settled_ts_ns):
      # Wait 5 min, then poll gamma at 30s intervals for up to 25 min
      await asyncio.sleep(300)
      for _ in range(50):  # 50 × 30s = 25 min
          truth = await asyncio.to_thread(gamma_resolution, snap.window_ts, ...)
          if truth in ("UP", "DOWN"):
              if truth != snap.original_resolution:
                  # Write a "settled-correction" record
                  self._log.record_settled_correction(
                      decision_id=snap.decision_id,
                      original_resolution=snap.original_resolution,
                      corrected_resolution=truth,
                      original_pnl=...,
                      corrected_pnl=...,
                      original_settled_ts_ns=original_settled_ts_ns,
                      corrected_ts_ns=self._clock_ns(),
                  )
              return
          await asyncio.sleep(30)

Schema decision: a NEW kind="settled_correction" record vs
overwriting the original "settled". Append-only is safer (preserves
audit history); the dashboard reads both and prefers correction
when available.

DecisionLog needs `record_settled_correction` method. Plus tests:

  - No correction when chainlink and gamma agree
  - Multiple corrections never written for same decision_id
